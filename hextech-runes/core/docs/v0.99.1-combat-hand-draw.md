# v0.99.1 战斗回合抽牌路径与 Mod Hook 调试

本文记录 **Slay the Spire 2 v0.99.1** 上「回合开始抽牌」在 `sts2.dll` 中的真实调用链，以及 HextechRunes 如何拦截。后续若有类似「改抽牌 / 自选抽牌 / 阻止抽牌」的海克斯，优先对照本文，避免重复反编译或误判 Hook 未命中。

证据来源：

- `versioned-dll-backups/0.99.1/game-refs/sts2.dll`（Mono.Cecil IL 分析，2026-06-28）
- 验牌（`CardInspectionRune`）本地复测与 `godot.log`

Last verified: 2026-06-28（STS2 **0.99.1**）。

---

## 1. 回合开始抽牌走什么

v0.99.1 上，**玩家回合开始的正常抽牌**（不是卡牌效果、遗物触发的额外抽牌）走下面这条链：

```text
CombatManager.SetupPlayerTurn          (async state machine: <SetupPlayerTurn>d__93)
  └─ Hook.BeforeHandDraw(combatState, player, choiceContext)
  └─ CardPileCmd.Draw(choiceContext, count, player, fromHandDraw: true)   // 四参数重载
       └─ 内部 state machine: CardPileCmd/<Draw>d__16
            ├─ Hook.ShouldDraw(...)
            ├─ 洗牌 / 手牌上限检查
            ├─ 从抽牌堆取牌 → Add 到手牌
            ├─ CombatHistory.CardDrawn(..., fromHandDraw)
            └─ Hook.AfterCardDrawn(..., fromHandDraw)
```

要点：

| 项目 | 说明 |
| --- | --- |
| **唯一回合抽牌入口** | `CombatManager/<SetupPlayerTurn>d__93` 是 v0.99.1 上 **唯一** 以 `fromHandDraw: true` 调用四参数 `CardPileCmd.Draw` 的 IL 调用点 |
| **`fromHandDraw` 语义** | `true` = 回合开始的手牌抽取；`false` = 卡牌 / 遗物 / 能力触发的额外抽牌 |
| **`Hook.BeforeHandDraw`** | 在 `Draw` 之前触发；遗物 / 能力可在此改状态，但**不会**替代抽牌 UI |
| **四参数 `Draw` 才是抽牌主 API** | 卡牌 `Acrobatics`、`Adrenaline` 等效果抽牌也走同一四参数重载，通常带 `fromHandDraw: false` |

## 2. `CardPileCmd.Draw` 两个重载（v0.99.1）

`sts2.dll` 中 `CardPileCmd` 有两个 public `Draw`：

| 签名 | 返回 | 回合开始是否使用 |
| --- | --- | --- |
| `Draw(PlayerChoiceContext, Player)` | `Task<CardModel>` | **否** |
| `Draw(PlayerChoiceContext, decimal count, Player player, bool fromHandDraw)` | `Task<IEnumerable<CardModel>>` | **是**（`fromHandDraw: true`） |

两参数重载主要用于例如 `UnceasingTop`、`Pendulum` 等「抽 1 张」场景，**不是**回合开始批量抽牌路径。

**Mod 侧结论**：改「回合开始抽什么牌」时，应 Hook **四参数** `CardPileCmd.Draw`，并在 prefix 里检查 `fromHandDraw == true`。不要只 Hook 两参数重载。

## 3. HextechRunes 当前拦截方式

### 3.1 Harmony Hook 安装点

文件：`src/Hooks/Combat/HextechCombatHooks.Install.cs`

```csharp
harmony.Patch(
    CardPileCmd.Draw(context, decimal, player, bool),  // 四参数
    prefix: DrawPrefix);
```

文件：`src/Hooks/Combat/HextechCombatHooks.Draw.cs`

- **`CardInspectionRune`（验牌）**：当 `fromHandDraw && count > 0` 且玩家持有该遗物时，prefix 返回 `false`，改走自选抽牌。
- **`NoNonsenseRune`（胡闹）**：当 `!fromHandDraw` 时拦截非回合抽牌（该符文在 v0.99.1-lite 注册表里仍 `Disabled`，Hook 逻辑保留供高版本）。

### 3.2 自选抽牌实现

文件：`src/HextechSelectedDrawHelper.cs`

流程概要：

1. `CombatCompat.ShouldDraw` → 对齐游戏 `Hook.ShouldDraw`
2. 计算手牌空位、`ShuffleIfNecessary`
3. **`CardSelectCmd.FromSimpleGrid`**（v0.99.1 / v0.100）展示抽牌堆供选择  
   - v0.99.1 **没有** `CardSelectCmd.FromCombatPile`
4. 逐张 `CardPileCmd.Add` 入手牌，并调用 `CombatCompat.RecordCardDrawn` / `AfterCardDrawn`

v0.99.1 兼容层：`src/Compat/CombatCompat.cs`（`ShouldDraw` 使用 `CombatState` 而非 `ICombatState`；手牌上限暂用常量 `10`）。

### 3.3 诊断日志

验牌 prefix 命中时会打：

```text
[INFO] [HextechRunes][CardInspection] selected draw count=<N> player=<NetId>
```

若选符成功但进战斗仍自动抽牌，**先查有没有这条日志**，再查 DLL 是否已部署。

## 4. 案例：验牌（CardInspectionRune）曾不生效的原因

### 4.1 现象

- 测试模式日志显示 `CARD_INSPECTION_RUNE` 已进入候选并被选中。
- 进战斗后回合开始仍自动抽牌，无「从抽牌堆选牌」UI。
- `godot.log` 无 `[CardInspection]`、无 `DrawSelectedFromDrawPile` 相关痕迹。

### 4.2 根因（两层）

1. **源码层（已修复）**  
   早期 v0.99.1-lite 曾用 `#if !STS2_99_1` 整段禁用 `DrawPrefix` / `HextechSelectedDrawHelper` 的 v0.99.1 路径。修复后改为：
   - 始终安装四参数 `Draw` prefix；
   - v0.99.1 用 `FromSimpleGrid` 替代 `FromCombatPile`。

2. **部署层（本次复测实际踩坑）**  
   游戏 `mods/HextechRunes_v0991_test/HextechRunes.dll` 仍是旧构建（例如 06/27 18:52），而新构建在 `dist/`（例如 06/28 10:10）。  
   构建脚本 deploy 时若游戏未关，会报：

   ```text
   Deploy copy failed for: HextechRunes.dll. Close Slay the Spire 2 and retry.
   ```

   **旧 DLL 不会包含验牌自选逻辑**，表现与「Hook 没写上」完全相同。

### 4.3 修复验证

1. 完全退出游戏 → 重新 `build_hextech_local.ps1` deploy。
2. 对比 deploy 目录与 `core/dist/HextechRunes.dll` 的时间戳 / SHA256。
3. Prismatic 选验牌 → 第一场战斗回合开始应出现选牌 UI。
4. 日志出现 `[HextechRunes][CardInspection] selected draw count=...`。

## 5. 类似海克斯的调试清单

按顺序做，可快速区分「选符问题 / Hook 问题 / 部署问题 / API 差异」：

### Step 0：确认遗物已拥有

- 日志或 UI 确认 `player.GetRelic<TYourRune>()` 在战斗中非 null。
- 选符链路问题见 `docs/v0.99.1-automation-smoke-test.md` 与 `HextechTestMode`。

### Step 1：确认部署的是新 DLL

```powershell
# 构建并部署（需先关游戏）
powershell -ExecutionPolicy Bypass -File .\local-tools\build_hextech_local.ps1 -SkipContentValidation

# 对比 hash（路径按本机调整）
Get-FileHash .\core\dist\HextechRunes.dll
Get-FileHash "E:\...\mods\HextechRunes_v0991_test\HextechRunes.dll"
```

### Step 2：确认 Hook 条件是否匹配抽牌类型

| 需求 | 应 Hook | prefix 条件 |
| --- | --- | --- |
| 仅改回合开始抽牌 | 四参数 `CardPileCmd.Draw` | `fromHandDraw == true` |
| 仅改卡牌/遗物额外抽牌 | 四参数 `CardPileCmd.Draw` | `fromHandDraw == false` |
| 抽牌前插入逻辑（不改 Draw） | 遗物/能力的 `BeforeHandDraw` | 在 `HextechRelicBase` 子类 override |
| 改抽牌数量 | `ModifyHandDraw` / `ModifyHandDrawLate` | 走 Mayhem / 遗物 hook 链 |

### Step 3：看日志

- Mod 初始化：`[HextechRunes] Loaded for Slay the Spire 2 0.99.1.`
- 验牌：`[HextechRunes][CardInspection] selected draw count=...`
- 无上述日志但选符正常 → 优先怀疑 **旧 DLL** 或 **prefix 条件未满足**（例如误判 `fromHandDraw`）。

### Step 4：必要时反编译 sts2.dll

工具：Mono.Cecil（或 ILSpy）。注意：

- 必须 **递归扫描 nested types**（async state machine 在 `Type/<Method>d__N` 里）；只扫顶层 `Types` 会漏掉 `SetupPlayerTurn` 与 `Draw` 调用关系。
- 搜索「谁以 `fromHandDraw: true` 调四参数 Draw」：在 `Call` 前若干条 IL 找 `ldc.i4.1`。

v0.99.1 当前结论：**只有** `CombatManager/<SetupPlayerTurn>d__93` 满足上述条件。

### Step 5：v0.99.1 API 差异

| 较新版本 | v0.99.1 |
| --- | --- |
| `CardSelectCmd.FromCombatPile` | **不存在** → 用 `FromSimpleGrid` |
| `CardPile.MaxCardsInHand` | **不存在** → `CombatCompat.MaxCardsInHand` |
| `Hook.ShouldDraw(ICombatState, ...)` | 使用 `CombatState` |

## 2026-07-04 Replay / destination compatibility notes

Confirmed policy:

- Extra play / replay counts are additive. Multiple replay sources should each add to `playCount`; they should not multiply each other.
- Card movement effects that return a played card to hand must wait until the final play in the replay series.
- In LAN multiplayer, Power-card replay is currently treated as unsafe for broad replay sources. The first mitigation keeps Attack/Skill replay enabled but skips additional Power-card replay in network combat for replay sources such as Bread and Cheese, Bread Sandwich, Ultimate Refresh, Tri Prism, Thought Overwrite, and Echo Form upgrade.
- Destination conflicts use this priority: a final result pile of `Exhaust` wins over Universal Scope returning the card to hand. This avoids Scope rescuing cards that another Hextech effect explicitly sent to Exhaust.

Known follow-up:

- The remaining multiplayer replay risk is deterministic random ordering for Jeweled Gauntlet when multiple players/replay sources are active. This is recorded for later validation, not fixed in this batch.
- Eight Penny Gate + Universal Scope should be tested explicitly: expected result is replay first, then Exhaust; Scope should not return the card to hand if the final result pile is Exhaust.

## 2026-07-04 Replay audit batch 3

Audit scope:

- `ModifyCardPlayCount` replay sources remain additive. No multiplicative replay source was introduced.
- `TwiceThriceRune` and `LightEmUpRune` count only first, non-auto attack plays via `IsFirstInSeries && !IsAutoPlay`; this matches replay-series semantics.
- `UniversalScopeRune` runs in `AfterCardPlayedLate` and checks `IsLastPlayInSeries`, so it does not move the card before all replays complete.
- `VampireCrawlerRune` now uses `HextechReplayCompat.IsLastPlayInSeries` instead of a hand-written play-index check.
- `FanTheHammerRune` now keeps its damage reduction active until the final play in the replay series, then clears it from `AfterCardPlayedLate`. This avoids relying on `CardModel.Played` event timing.

Remaining risks:

- `JeweledGauntletRune` and `UniversalScopeRune` both use deterministic random with combat proc ordinals. This is safer than local random, but still needs multiplayer log validation when Host and Client evaluate modifiers for remote player actions. If desync remains, the next design step is Host-authored replay/refund decisions rather than local ordinal consumption.
- `HextechPlayerSlowPower` currently increments on every `AfterCardPlayed`, including replay instances. This may be intentional because replayed cards are actual plays, but if LAN logs show Slow divergence it should be re-audited separately.
